# 기존 프로젝트 분석과 실험 사전 결정

이 문서는 기존 소스와 저장 결과를 조사한 뒤 결정한 범위를 기록한다. 실제 튜닝 결과에 따라 탐색 공간이나 선택 기준을 바꾸지 않는다. 실제 파일 해시와 확인한 원자료는 `audit/existing_audit.json`, 원본 보존 기준은 `audit/legacy_manifest.json`에 있다.

## 데이터와 모델

기본 입력은 루트의 2전하 `charge_dataset.npz`가 아니라 `Models/charge_dataset_5charges_v9.npz`다. 현재 배열은 G00 `(10000, 32, 32)`, G05 `(10000, 32, 3)`, target `(10000, 5, 4)`로 로드된다. 생성 seed는 `20260827`, 관측 후보는 32개다.

전하 위치 x/y는 −1.5~1.5, z는 0.1~1.5이며 크기는 0.3~1.0, 부호는 양/음이다. 관측 평면의 전위 제곱 G00과 희소한 부호 있는 전위 G05를 입력한다. z>0 제약은 평면의 상하 반사 모호함을 제거한다. 전하 순서를 식별자로 쓰지 않으며 120개 순열의 공동 비용으로 정답에 대응한다.

`NewLearning9.py`가 데이터 검사, train-only 정규화, mask, 물리 손실과 지표를 정의한다. `ModelExperiment10.py`는 동일한 physics를 이용한 routing 비교와 dropout·조기 종료·전체 epoch 체크포인트 저장 기능을 제공한다.

Sign-only의 구조 출력(위치·크기·상대부호)은 G00만 사용하고 전체부호는 G05만 사용한다. Full은 G05의 전체 부호 반전에 불변인 특징을 구조에 추가한다. 두 모델의 등록 파라미터 수는 406,969개로 같지만 sign-only의 context 모듈 45,440개는 구조 계산에 사용되지 않는다. 따라서 활성 용량까지 같다고 주장하지 않는다. 이번 튜닝은 그 구조를 바꾸지 않는다.

## 성능 저하와 하이퍼파라미터의 관련성

기존 정식 36회 학습은 모두 300 epoch이고 최저 검증 구조 손실의 epoch는 25~42였다. 한 대표 사례(full / G05 100% / seed 43)는 26 epoch 이후 train 구조 손실이 0.516232에서 0.092933으로 감소하는 동안 validation 구조 손실이 0.597517에서 1.002909로 증가했다. 학습 부족만으로 설명하기 어려운 과적합 양상이다.

과거 저장 이력을 독립적으로 읽은 현재 audit에서도 같은 유형의 격차를 확인했다. 구조 악화 비율이 가장 큰 full / G05 25% / seed 42는 best validation 0.598759에서 마지막 1.062227로 커진 반면 train은 best epoch의 0.461529에서 마지막 0.107445로 내려갔다. 과거 test 값을 최적 조합을 정하는 함수에 전달하지 않았다.

기존 14개 pilot에서 dropout 0.1의 full 평균 best validation 구조 손실은 0.604931 → 0.587185였고 sign-only는 0.598194 → 0.600591이었다. Full의 이득도 위치 손실 감소가 주도하며 상대부호 NLL은 악화되는 경우가 있었다. 따라서:

- 학습률·정규화 강도가 과적합과 일반화의 일부에 영향을 줄 가능성이 충분하다.
- 조기 종료는 이미 저장된 best 모델 자체를 개선하는 방법이 아니라 불필요한 후반 학습을 줄이는 제어다.
- dropout 하나를 공통 기본값으로 강제하거나 위치만 좋아진 것을 부호까지 전부 개선됐다고 표현하면 안 된다.
- 구조/관측의 한계도 남아 있으므로 하이퍼파라미터가 성능 저하의 유일한 원인이라고 단정하지 않는다.

## 기존 결과를 그대로 baseline으로 쓰지 않는 이유

현재 데이터 바이트 SHA-256은 `f90880bbbcd31c528c0603a2aa8043c0ddea567c393d83fc59ae3afd3ac24863`이고 pilot 기록은 `12453caa0ec01dff00f6265ffe65724346b8ebd09bedb8c795f3cd6b45b255c4`다. 현재 train 정규화 값은 세 pilot 배치와 정확히 같았다. 바이트 해시 차이가 표본 차이를 뜻한다고 확정할 수 없지만 당시 배열 해시가 없어 배열 전체의 동일성을 입증할 수도 없다.

기존 pilot 환경은 Python 3.14.7 / PyTorch 2.11.0+cu128 / CUDA 12.8이고 현재 실제 동작 환경은 Python 3.12.13 / PyTorch 2.7.0+cu126 / CUDA 12.6 / RTX 3070이다. 같은 seed라도 환경 변화 후 수치가 같다고 가정하지 않는다. [PyTorch의 재현성 보장 범위](https://docs.pytorch.org/docs/2.7/notes/randomness.html).

현재 로컬 routing 체크포인트는 36개이며 v10 정식 체크포인트는 없었다. 두 모델의 기존 `best_structure.pt`를 직접 열어 v9 프로토콜, 선택 epoch, 전체 모델 텐서의 유한성을 확인했다. 이 가중치를 초기값으로 사용하지 않는다. 후보마다 같은 seed로 **처음부터** 초기화해 동일 환경의 baseline과 비교한다.

## 탐색 설계

독립적인 학습률·감쇠·dropout의 조합을 작은 예산에서 확인하기 위해 과거 근거가 있는 6개 anchor와 seed가 고정된 로그 균등 난수 후보 2개를 사용한다. 수많은 조합을 모두 격자로 실행하지 않고 실제 후보와 결과를 명시적으로 보존한다. 제한된 계산 예산에서 random search를 사용하는 일반적 근거는 [Bergstra와 Bengio의 원 논문](https://www.jmlr.org/papers/v13/bergstra12a.html)에 있다. 이번 범위·후보 수·선택 기준 자체는 이 프로젝트의 기존 이력과 측정 비용을 바탕으로 정했다.

전체 8,000 train / 1,000 validation의 실제 GPU epoch를 사전 측정한 결과 첫 epoch 약 1.07초, 다음 두 epoch 약 0.73~0.76초였다. 이 측정은 기준 설정의 첫 3 epoch만 확인한 실행 점검이고 후보 선택이나 최종 성능 주장에 쓰지 않는다. 정식 튜닝은 epoch별 체크포인트 쓰기 비용도 포함한다.

이전 dropout 0.2의 최적점이 72 epoch였으므로 매우 짧은 epoch 예산으로 후보를 탈락시키지 않는다. 각 후보의 상한을 150 epoch로 같게 두고, 1-seed screening 뒤 선택된 후보의 seed를 늘린다. Baseline도 같은 상한·patience를 쓰며 초기화와 shuffle seed를 쌍으로 맞춘다.

일차 지표는 기존 손실 가중치를 그대로 쓴 `validation.structure`다. 위치·크기·상대부호를 함께 다루는 기존 가설을 유지하고 전체부호 분기의 학습률 제어와 연결하지 않는다. 실제 단위 위치 오차, 상대부호·전체부호·절대부호 정확도, 손실 성분을 모두 추가 기록해 복합 손실과 개별 지표의 상충을 드러낸다. `best_total.pt`는 독립적으로 저장·평가하지만 일차 선택 기준으로 바꾸지 않는다.

G05 fraction도 하이퍼파라미터로 골라 데이터가 많은 조건을 최적 모델로 선전하지 않는다. 기본 연구 범위는 기존 pilot과 같은 G05 100%다. 다른 fraction을 연구하려면 실행 전 spec에 그 범위를 정해 모든 후보·모델·seed에 똑같이 적용해야 한다.

## 누수와 재현성 점검

현재 split의 인덱스는 80/10/10으로 겹치지 않고 모든 표본을 한 번씩 포함한다. 10,000개 G00 전체에서 완전히 같은 표본은 0개였으며 분할 사이 중복도 0개다. 반복 관측이나 동일 물리 구성의 정확한 복사본이 분할을 가로지르면 파이프라인은 거부한다. 이 검사는 유사하지만 동일하지 않은 물리 구성의 임의적인 독립성을 증명하는 것은 아니다.

분할·정규화·모델·손실·평가를 고정하고, 모든 설정·환경·소스·배열 해시를 저장한다. 중단·재개는 마지막 epoch의 원자적 체크포인트 하나를 기준으로 복원한다. `latest.pt` 저장 뒤 부수 파일을 쓰는 도중 중단돼도 두 best 상태와 이력을 그 체크포인트로 다시 게시한다.

최종 결정은 검증 결과만으로 seal한 `selection.json`이며, 결과/체크포인트가 바뀌면 최종 평가가 거부된다. 결과를 본 뒤 더 유리한 시험 데이터를 선택하거나 모델을 재학습하는 경로는 없다.

과거 테스트셋은 이미 보고서에서 분석된 적이 있어 이번 연구의 완전히 새 holdout으로 볼 수 없다. 별도 seed와 같은 물리 분포·센서에서 생성한 fresh holdout을 설정 결정 이후에 열어 이 한계를 줄인다. 이 fresh holdout도 한번 본 후에는 향후 설계를 위한 새 독립 평가 자료로 간주할 수 없다.
